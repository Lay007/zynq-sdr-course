# Лабораторная 11.8 — Overlay gpreg BPSK для AD9361 и первый разведочный пакет

## Цель

Перейти от заглушки запуска через AXI-Lite к первому специфичному для курса аппаратному overlay AD9361, который сохраняет видимую для PS плоскость управления, пока восстанавливается точно подходящий к плате загрузочный shell:

```text
PS / software -> axi_gpreg @ 0x79040000 -> staged sample-domain bridge -> AD9361 TX/RX path
```

Эта работа — первая чистая передача от исполняемого модема Блока 5 к импортированному вендорскому shell AD9361, соответствующему реальной плате курса (`xc7z020clg400-2`). Место работы в общей истории Блока 11 — на [карте лабораторных Блока 11](../blocks/11-integrated-sdr-project.md).

## Инженерное решение

По состоянию на `2026-06-21` закоммиченный режим overlay намеренно сведён к `gpreg_only`.

Этот откат сделан сознательно:

- он держит путь управления простым и проверяемым;
- он сохраняет видимую для Linux оболочку RX и TX DMA, чтобы стоковое дерево устройств по-прежнему нормально опознавалось;
- он отделяет проверку карты адресов `axi_gpreg` от более трудной проблемы чистой загрузки AD9361;
- он не позволяет считать пересобранный, но ещё не безопасный для загрузки образ PL допустимой базовой линией RF-измерений.

Прежние эксперименты с TX с включённым пакетом остаются полезным историческим доказательством, но не являются текущей безопасной закоммиченной базой. Следующий шаг с контрольной точкой — пока считать извлечённую полезную нагрузку стокового раздела BOOT единственной внешне загружаемой безопасной для загрузки опорой, а затем объяснить, почему редактируемые shell, соотнесённые с исходниками, всё ещё теряют AD9361, прежде чем продолжать разведку RF.

## Контракт регистров

Базовый адрес: `0x79040000`

| Смещение | Смысл |
|---|---|
| `0x000` | регистр версии `axi_gpreg` |
| `0x004` | регистр ID `axi_gpreg`, ожидается `0x4250534B` |
| `0x404` | выход GPREG0: управляющее слово; бит `0` — фронт старта, бит `1` — сброс залипающего done, биты `3:2` — режим решения RX (`I`, `-I`, `Q`, `-Q`) |
| `0x408` | вход GPREG0: слово статуса; бит `0` — синхронизированный уровень старта, бит `1` — busy, бит `2` — залипающий done, бит `3` — залипающий таймаут/прерывание RX |
| `0x444` | выход GPREG1: `FRAME_BIT_COUNT` |
| `0x448` | вход GPREG1: `RECEIVED_BITS` |
| `0x484` | выход GPREG2: `PREAMBLE_COUNT` |
| `0x488` | вход GPREG2: `TOTAL_ERRORS` |
| `0x4C4` | выход GPREG3: `START_OFFSET` |
| `0x4C8` | вход GPREG3: `PAYLOAD_ERRORS` |
| `0x508` | вход GPREG4: подпись моста, ожидается `0x4250534B` |
| `0x548` | вход GPREG5: упакованные `TX_VALID_COUNT` и отладка знака решений RX |
| `0x588` | вход GPREG6: `RX_VALID_COUNT` на стороне моста |
| `0x5C8` | вход GPREG7: упакованное слово `CAPTURE_DEBUG` сырого отвода RX |

`GPREG5` теперь упаковывает ещё одно свидетельство времени работы рядом с младшими 12 битами `TX_VALID_COUNT`:

- биты `11:0`: `tx_valid_count_lsb12`;
- биты `19:12`: младшие 8 бит счётчика восстановленных бит `1`;
- биты `27:20`: младшие 8 бит счётчика валидных восстановленных бит;
- бит `28`: встречался ненулевой входной отсчёт жёсткого решения;
- бит `29`: встречался отрицательный входной отсчёт жёсткого решения;
- бит `30`: встречался восстановленный бит `1`;
- бит `31`: встречался импульс валидности восстановленного бита.

`CAPTURE_DEBUG` упаковывает одно компактное слово-свидетельство времени работы:

- бит `31`: встречался сырой импульс `capture_in_valid`;
- бит `30`: встречался ненулевой сырой отсчёт `RX1 I/Q`;
- бит `29`: встречался сырой импульс `capture_in_valid`, пока ядро BER было активно;
- бит `28`: сырой отсчёт `RX1 I` на отводе моста бывал отрицательным;
- бит `27`: сырой отсчёт `RX1 Q` на отводе моста бывал отрицательным;
- биты `26:14`: младшие 13 бит счётчика сырых импульсов `capture_in_valid`;
- биты `13:0`: пиковый модуль сырого отсчёта `RX1` в беззнаковых единицах Q14.

Наблюдённые факты после повторной инициализации на плате:

- сразу после горячей загрузки регистр запроса RX common откатывался к `rx_common_ctrl_req = 0x00000000`, а соответствующие чтения `rx_common_clk_count` / `rx_common_status` были нулевыми;
- восстановление стокового слова запроса `0x79020040 <- 0x00000003` немедленно оживило ненулевую активность тактирования/статуса RX: `rx_common_clk_count = 0x00013AE5` и `rx_common_status = 0x00000005`;
- та же повторная инициализация сняла и свидетельство сброса на сырой входной стороне: `adc_input_reset_asserted_current` упал в `false`, а отладочные слова входной стороны и отвода RX снова стали ненулевыми;
- несмотря на это восстановление на стороне fabric, отдельный A/B-помощник по-прежнему воспроизводил те же хостовые отказы после горячей загрузки: прямой `libiio Buffer.refill()` по-прежнему выбрасывал `OSError: [Errno 110] host unreachable`, а `iio_readdev` по-прежнему завершался `Unable to refill buffer: Unknown error (110)`;
- затем свидетельство с хостовым TX при повторной инициализации доказало, что overlay во время работы больше не голодает на отводе отсчётов: `rx_valid_count` стал ненулевым, сырое слово `CAPTURE_DEBUG` показало валидную/ненулевую активность, и мост снова видел поток RX во время стокового хостового TX;
- первая закоммиченная развёртка `start_offset` после этой повторной инициализации нашла реальное окно приёма полного кадра на первой попытке после TX: `start_offset = 32` завершил `281` принятый бит со `144` общими ошибками и `136` ошибками нагрузки, а следующие попытки в той же сессии TX откатывались к поведению, похожему на тайм-аут;
- более широкая развёртка в свежей сессии затем исключила простую вину `start_offset`: смещения от `0` до `576` давали тот же результат `281 / 144 / 136` с одинаковыми `rx_valid_count = 2982` и `capture_peak_abs_max_q14 = 4095`;
- новое упакованное свидетельство знака решений наконец сделало вид отказа явным на приёме полного кадра: тракт восстановленных бит выдавал импульсы валидности, вход жёсткого решения был ненулевым, но никогда не становился отрицательным и никогда не давал восстановленной `1`, так что живые счётчики BER фактически сравнивали ожидаемый кадр с полностью нулевым потоком восстановленных бит.

Первопричина — offset-binary, и перенастройка после исправления, `2026-06-23`:

- более строгое свидетельство знака сырых отсчётов `docs/assets/lab120_runtime_capture_sign_single_point_live_20260623.json` затем показало, что сам сырой отвод моста никогда не становился отрицательным, хотя `capture_peak_abs_max_q14 = 4095`; это исключило мёртвый тракт RX и указало на несовпадение формата отсчётов;
- просмотр импортированного HDL ADI (`ad_datafmt.v` и `up_adc_channel.v`) объяснил причину: при оставленных по умолчанию нулевых настройках формата данных RX приёмный тракт `axi_ad9361` выдаёт на отвод моста сырые 12-битные отсчёты в коде со смещением (offset-binary), а не знаковые отсчёты в дополнительном коде;
- теперь мост локально исправляет эти младшие 12 бит перед подачей в `bpsk_zynq_ber_top`, а `CAPTURE_DEBUG` намеренно по-прежнему сообщает сырой неформатированный отвод, чтобы объяснение на уровне исходников оставалось проверяемым;
- непосредственное живое доказательство после исправления `docs/assets/lab121_runtime_offset_binary_fix_single_point_live_20260623.json` показало, что прежний отказ с полностью нулевым потоком действительно ушёл: на железе теперь появляются `decision_negative_seen_any = true` и `recovered_one_seen_any = true`;
- оставшийся BER всё ещё высок, но теперь поддаётся настройке, а не схлопнут: `docs/assets/lab122_runtime_offset_binary_fix_phase_sweep_live_20260623.json` улучшил лучшую точку до `281 / 129 / 120` при `start_offset = 34`, `docs/assets/lab123_runtime_offset_binary_fix_tx_phase_sweep_live_20260623.json` показал лишь скромный дополнительный выигрыш от фазы TX, а `docs/assets/lab124_runtime_offset_binary_fix_gain_sweep_live_20260623.json` достиг текущей лучшей живой точки `281 / 127 / 114` при `start_offset = 34`, `tx_phase = 315 deg`, `rx_gain = 5 dB`.

Продолжение с самотактируемым `bridge_txrx_mux`, `2026-06-23`:

- новый помощник времени работы `blocks/block_11_integrated_sdr_project/python/lab_11_19_runtime_bridge_txrx_self_timed_bringup.py` убирает зависимость от асинхронного хостового циклического TX: он горячо загружает `bridge_txrx_mux`, восстанавливает `rx_common`, настраивает AD9361 и запускает пакет со стороны PL тем же управляющим словом `start`;
- первое доказательство самотактируемого пути в одной точке `docs/assets/lab125_runtime_bridge_txrx_self_timed_single_point_live_20260623.json` показало, что этот путь теперь завершает полный кадр из `281` бита без тайм-аута; это достаточно закрывает прежнее опасение «кадр пропадает, потому что TX асинхронный», чтобы продолжать отлаживать BER на самом детерминированном пути;
- остаточный BER всё ещё не низкий, поэтому следующий лёгкий эксперимент добавил выбираемые из плоскости управления режимы решения RX через биты `3:2` GPREG0;
- разведочная развёртка режимов `docs/assets/lab126_runtime_bridge_txrx_self_timed_mode_sweep_live_20260623.json` предполагает, что на самотактируемом пути `neg-i` лучше режима по умолчанию `i`, а последующий чистый повтор `docs/assets/lab126_runtime_bridge_txrx_self_timed_neg_i_single_point_live_20260623.json` показывает, что путь по-прежнему доходит до полного кадра, но остаётся чувствительным к сессии.

Текущая закоммиченная базовая линия безопасности:

- стоково-безопасный путь восстановления по-прежнему `hardware/7020_ad936x_sdr/stock_system_top_from_BOOT.bin`; при старом запасном варианте `uEnv.txt` с `loadb` для `.bit.bin` он не доказывал произвольную внешнюю замену PL, но при новом ручном пути UART `fpga load` он теперь единственный продемонстрированный внешне загружаемый кандидат, безопасный для загрузки;
- извлечённый стоковый раздел BOOT также единственная внешне загружаемая полезная нагрузка PL, которая сейчас проходит ручной UART `fpga load` с живым AD9361; см. `docs/assets/lab112_clean_boot_pl_validation.json`;
- автономный вендорский эталон `hardware/7020_ad936x_sdr/ps/ad936x_no_os_reference/platform/hw/system_top.bit` остаётся соотнесённым с исходниками сырым контрольным кандидатом, но по-прежнему теряет AD9361 и как сырой `fpga loadb`, и как ручной `.bit.bin` `fpga load`;
- `hardware/7020_ad936x_sdr/boot/validate_clean_boot_overlay.py` фиксирует решающее доказательство UART для сырого `fpga loadb`, а `hardware/7020_ad936x_sdr/boot/validate_manual_uart_fpga_load.py` теперь покрывает ручной путь `.bit.bin` `fpga load`;
- пересобранный shell `vendor_only` теперь тоже проходит создание проекта Vivado, реализацию, генерацию bitstream и экспорт XSA, но по-прежнему не проходит чистую загрузку с тем же тайм-аутом калибровки AD9361;
- новый режим `bridge_rx_only` теперь проходит создание проекта Vivado, реализацию, генерацию bitstream и экспорт XSA;
- сохранённый снимок вендорского `zc702.xpr`, пересобранный через `hardware/7020_ad936x_sdr/rebuild_vendor_xpr_snapshot_mio_patch.tcl`, по-прежнему экспортирует XSA без расхождений модулей/диапазонов памяти/параметров с вендорским эталоном, но его прямая загрузка сырого `system.bit` по-прежнему не проходит чистую загрузку AD9361 с тем же тайм-аутом калибровки;
- более новый кандидат чистой загрузки сырого `bridge_txrx_mux` теперь доказывает, что собственный overlay курса действительно доходит до PL и предоставляет `axi_gpreg` на плате после перезагрузки; см. `docs/assets/lab118_axi_gpreg_bringup_cleanboot_raw.json`;
- ранний сгенерированный помощником кандидат `bridge_txrx_mux.bit.bin` был отвергнут U-Boot `fpga load` с `zynq_validate_bitstream: Bitstream is not validated yet (diff 1700)`, поэтому последующее здоровое состояние AD9361 на этом пути было от нетронутого стокового shell PL;
- после исправления преобразования `.bit -> .bit.bin` в правильную полезную нагрузку с перестановкой слов заново сгенерированный кандидат `bridge_txrx_mux.bit.bin` теперь принимается ручным UART `fpga load`, но Linux по-прежнему попадает в тот же тайм-аут калибровки AD9361 и предоставляет только `iio:device0`;
- заново сгенерированные кандидаты для загрузки из `AD936X_PL.zip` и `AD936X_only_PL.zip` были отвергнуты и сведены в `docs/assets/lab112_clean_boot_pl_validation.json`.

Интерпретация:

- плоскость управления gpreg от PS к PL была проверена на реальном железе хотя бы один раз в раннем overlay с включённым пакетом;
- та же плоскость управления gpreg теперь читается и после прямой чистой загрузки сырого кандидата `bridge_txrx_mux`: ID и подпись равны `0x4250534B`, `tx_valid_count > 0`, `rx_valid_count == 0`;
- исправленная перезагрузка через `fpga_manager` во время работы теперь воспроизводит то же чтение gpreg из стокового shell Linux без потери базового перечисления устройств IIO, поэтому препятствие уже не в том, что «плата вообще не видит overlay»;
- сравнение стокового и загруженного во время работы образа теперь доказывает, что стоковый shell Linux до любой перезагрузки поддерживает оба пути хостового приёма RX, а горячая загрузка ломает оба, хотя `axi_gpreg` остаётся видимым;
- уточнённое свидетельство `bridge_rx_only` во время работы добавляет более сильный отрицательный результат: даже когда стоковый вендорский тракт TX успешно передаёт общий пакет BPSK, мост по-прежнему видит `rx_valid_count = 0`, а слово `CAPTURE_DEBUG` сырого отвода RX остаётся нулевым;
- результат повторной инициализации RX common во время работы сильнее прежнего отрицательного свидетельства: тракт RX на стороне fabric теперь можно оживить после горячей загрузки, но хостовый путь приёма libiio/DMAC по-прежнему сломан;
- первая развёртка `start_offset` после повторной инициализации показывает, что приёмный тракт BPSK во время работы теперь достаточно жив, чтобы завершить попытку приёма полного кадра из `281` бита, поэтому препятствие уже не в мёртвой проводке RX;
- объяснение с offset-binary закрывает эту конкретную ошибку: приёмная цепочка больше не застревает на беззнаковых сырых отсчётах AD9361, и отрицательные решения / восстановленные биты `1` теперь появляются на железе;
- новый результат с самотактируемым `bridge_txrx_mux` снимает прежнее объяснение «вся проблема в хостовом циклическом TX»: полные кадры теперь воспроизводятся без тайм-аута на тракте TX/RX, принадлежащем PL, но BER всё ещё зависит от полярности решения и дрейфует между сессиями;
- поэтому следующее препятствие — более узкая проблема на стороне приёма: стабилизировать детерминированный самотактируемый путь, затем решить, нужен ли следующим шагом чуть более развитый каскад коррекции фазы/оси или настоящий детектор преамбулы/кадра в приёмном тракте FPGA;
- нормализованный поток `vendor_only` на чистом Tcl теперь устраняет прежнее расхождение `MIO14/15`, но по-прежнему заблокирован четырьмя производными параметрами, доступными только для чтения или отключёнными: `sys_ps7.PCW_S_AXI_HP0_FREQMHZ`, `axi_ad9361_adc_dma.DMA_AXI_PROTOCOL_SRC`, `axi_ad9361_dac_dma.DMA_AXI_PROTOCOL_DEST` и `axi_ad9361.SPEED_GRADE`; см. `docs/assets/vendor_reference_vs_vendor_only_handoff_diff.json`;
- сохранённый снимок вендорского `zc702.xpr` после пересборки через поток правки MIO14/15 по-прежнему предпочтительный редактируемый источник-свидетель, но ещё не безопасная для загрузки RF-базовая линия; см. `docs/assets/vendor_reference_vs_vendor_xpr_mio14_15_patch_handoff_diff.json`;
- текущий закоммиченный HDL теперь также включает промежуточный режим повторной интеграции `bridge_rx_only`, проверенный в Vivado, но ещё не при чистой загрузке;
- извлечённый из `BOOT.bin` стоковый раздел теперь единственная внешне загружаемая безопасная для загрузки опора повторной интеграции, но он ещё недостаточно редактируем и недостаточно соотнесён с исходниками для итогового overlay курса;
- ближайшая задача — убрать оставшуюся неоднозначность асинхронного кадра из пути BER во время работы, затем продолжить перенастройку тайминга / фазы при уже закрытой ошибке формата отсчётов, параллельно продолжая исследование безопасного для загрузки shell для редактируемого пути чистой загрузки.

## Следующий порядок повторного включения (по этапам)

1. Убедиться, что кандидат пользовательского загрузочного образа PL принимается соответствующим валидатором: сырой `.bit` через `validate_clean_boot_overlay.py` либо `.bit.bin` через `validate_manual_uart_fpga_load.py`.
2. Подтвердить IP платы, регистр ID `axi_gpreg` и подпись моста до записи параметров кадра.
3. Снова включить мост домена отсчётов, сохраняя видимую для Linux оболочку DMA неизменной.
4. Держать ослабление TX AD9361 на минимальной доступной мощности.
5. Держать усиление RX низким и ручным. Не включать AGC для первого возобновлённого пакета.
6. Запустить только один короткий пакет.
7. Наблюдать `busy`, затем `done` либо `done после таймаута`.
8. Прочитать `RECEIVED_BITS`, `TOTAL_ERRORS` и `PAYLOAD_ERRORS`.
9. Только после этого возобновлять повторные развёртки или кампании BER.
