# Лабораторная 5.11 — Обёртка управления AXI-Lite для BPSK BER верхнего уровня

## Цель

Открыть детерминированный верхний уровень BPSK BER для плоскости управления в стиле Zynq Processing System:

```text
PS / ПО -> регистры AXI-Lite -> кадровое BPSK BER-ядро -> граница отсчётов TX/RX
```

Это управляющий компаньон Lab 5.10. Тракт данных DSP остаётся тем же, но команда запуска, параметры тайминга и результаты BER теперь проходят через компактный интерфейс регистров, отображённых в память.

## Карта регистров

| Адрес | Имя | Доступ | Смысл |
|---|---|---|---|
| `0x00` | `CONTROL_STATUS` | `W/RO` | бит `0`: запись `1` запускает один кадр; бит `1`: `busy`; бит `2`: `done` (залипающий), сбрасывается записью `1` в бит `2` |
| `0x04` | `FRAME_BIT_COUNT` | `RW` | число передаваемых и сравниваемых бит |
| `0x08` | `PREAMBLE_COUNT` | `RW` | число бит преамбулы, исключаемых из payload BER |
| `0x0C` | `START_OFFSET` | `RW` | детерминированный индекс отсчёта согласованного фильтра для решений по символам |
| `0x10` | `RECEIVED_BITS` | `RO` | число восстановленных бит в последнем завершённом прогоне |
| `0x14` | `TOTAL_ERRORS` | `RO` | полное число битовых ошибок в последнем завершённом прогоне |
| `0x18` | `PAYLOAD_ERRORS` | `RO` | битовые ошибки только payload в последнем завершённом прогоне |
| `0x1C` | `ID` | `RO` | фиксированное идентификационное слово `0x4250534B` |

## Назначение интерфейса

Эта обёртка предназначена для управления на низкой скорости, а не для массовой передачи отсчётов:

- AXI-Lite настраивает запуск кадра и считывает счётчики BER;
- поток отсчётов остаётся на явной границе TX/RX из Lab 5.10;
- будущий проект может подключить эту границу к AD9363, DMA или потоковому мосту.

## Почему этот этап важен

Ранние работы доказали, что логика модема работает. Эта работа доказывает, что плоскость управления тоже готова к интеграции:

1. ПО может запрограммировать детерминированную конфигурацию кадра;
2. ПО может запустить ровно один пакет;
3. ПО может опрашивать `busy` и `done`;
4. ПО может считать счётчики BER после завершения пакета.

Это минимальный контракт регистров, необходимый, прежде чем передавать проект настоящему Zynq PS или слою ПО no-OS.

## Стратегия testbench

Самопроверяющийся testbench:

1. читает общие детерминированные метаданные;
2. записывает регистры конфигурации кадра по AXI-Lite;
3. запускает один пакет через управляющий регистр;
4. замыкает отсчёты TX на отсчёты RX;
5. опрашивает регистр статуса, пока не установится залипающий бит `done`;
6. проверяет нулевой BER и затем сбрасывает залипающий флаг `done`.

## Интерпретация с точки зрения железа

Первое применение на железе простое:

```text
PS записывает регистры AXI-Lite -> запускается один короткий детерминированный пакет -> тракт AD9363 TX/RX или внешний монитор наблюдает результат
```

Это правильное место для подключения ПО no-OS, регистровых обращений из пользовательского пространства Linux или небольшого драйвера.

## Порядок первого подключения AD9363

Используйте существующие инструменты репозитория как путь запуска:

1. Опросите удалённый контекст IIO командой `python blocks/block_06_rf_frontend_and_ad9363/python/lab_6_3_probe_iio_context.py --uri ip:192.168.40.1`.
2. Примените консервативную RF-политику Блока 6.3: минимальная мощность TX, низкое ручное усиление RX, AGC выключен и только короткий пакет.
3. Сначала прочитайте регистр AXI-Lite `ID`, затем запрограммируйте `FRAME_BIT_COUNT`, `PREAMBLE_COUNT` и `START_OFFSET`.
4. Запишите `1` в `CONTROL_STATUS[0]`, опрашивайте `busy`, затем дождитесь залипающего `done`.
5. Используйте контролируемый RX-тракт Zynq для счётчиков BER, а RTL-SDR оставьте наблюдателем только за спектром во время первой OTA-проверки.

Так разведочный прогон остаётся небольшим и детерминированным перед переходом к более длинным пакетам или количественному измерению BER.

## Чего ожидать

```text
PASS: bpsk_zynq_ber_axi_lite completed without errors
```

Testbench играет роль PS: читает регистр ID, проверяет, что control/status после сброса равен нулю, записывает и читает обратно число бит кадра, число бит преамбулы и начальное смещение, запускает прогон битом 0, опрашивает статус, пока не увидит и `busy` (бит 1), и `done` (бит 2), проверяет `received_bits` и нулевые общие ошибки и ошибки полезной нагрузки, сбрасывает залипающий `done` записью бита 2 и убеждается, что TX-отсчёты были сформированы.

Раннер курса генерирует векторы, компилирует, запускает симуляцию и считает ошибкой любую строку `FAIL` или ненулевой код выхода симулятора:

```bash
python tools/run_block5_hdl_smoke.py --test tb_bpsk_zynq_ber_axi_lite
```

## Упражнения

Каждое упражнение ниже — намеренная мутация RTL в одну строку. Внесите её, запустите testbench, прочитайте сообщения и верните файл (`git checkout -- <file>`). Приведённые выводы получены на Icarus Verilog 12.0.

1. Сделайте `done` несбрасываемым: в `bpsk_zynq_ber_axi_lite.v` замените `if (wstrb_latched[0] && wdata_latched[2]) begin` на `if (1'b0) begin`. Testbench сообщает `ERROR: done sticky bit did not clear`. На железе программа, опрашивающая `done`, считала бы каждый следующий прогон уже завершённым.
2. Поменяйте местами биты `busy` и `done` при чтении статуса (`{29'd0, core_busy, done_sticky, 1'b0}`). Testbench сообщает `ERROR: busy bit was never observed during the AXI-Lite controlled run`. Тракт данных не тронут, и проект бы синтезировался, поэтому такую ошибку ловит только проверка карты регистров.
3. Напишите ту же последовательность как короткую функцию на C с 32-битными чтениями и записями в стиле `devmem` и тайм-аутом опроса. Какой регистр вы читаете, чтобы решить, что прогон закончен, и что будет, если прочитать его только один раз?
