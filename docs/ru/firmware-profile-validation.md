# Проверка профилей прошивки

Сценарий реализует первый, офлайн-этап [issue #81](https://github.com/Lay007/zynq-sdr-course/issues/81)
и [ADR 0004](../adr/0004-zynqsdr-firmware-profiles.md).
Он готовит доказательства для стенда Zynq-7020/AD936x, без переключения прошивок.
[English version](../en/firmware-profile-validation.md).

## Уровни доказательств

| Доказательство | Что подтверждает | Что остаётся открытым |
| --- | --- | --- |
| Совпали manifest и SHA-256 | Перечисленные файлы имеют записанное содержимое | Внешние зависимости, совместимость загрузки |
| Совпали oid/size LFS-поинтера | Идентичность записанного объекта | Проверка скачанных байтов |
| Статическая инвентаризация `uEnv.txt` | Объявленные пути и повторные присваивания | Исполняемый путь загрузки и постоянные настройки U-Boot |
| Перечисление IIO на плате | Устройства, каналы и читаемые настройки на тот момент | Физические clocks, DMA, идентичность FPGA, RF |
| Протокол загрузки и отката для платы | Проверенная последовательность для данной платы и комплекта | Другие платы и версии образов |
| Защищённый RF-эксперимент | Измеренные параметры в записанных условиях | Другие усиления, частоты и радиотракты |

Храните `archive_status`, `boot_tested`, `rf_measured` и `currently_deployed` раздельно.
Старая запись о развёртывании не определяет сегодняшний образ на плате.
Имена платы и профиля, введённые оператором, являются заявлениями, а не результатом обнаружения.

## Кандидаты из архива

Приватный репозиторий артефактов хранит ссылки на манифесты, контрольные суммы,
реестр и датированную инвентаризацию. Публичный курс содержит методику и синтетические примеры.

| Кандидат | Что ещё нужно установить |
| --- | --- |
| `vendor-pluto` | Полные vendor-зависимости загрузки и baseline каждой платы |
| `vendor-zynqsdr-legacy` | Выбор корневого/вложенного SD-варианта и недостающие зависимости |
| `course-fpga` | Полный boot set и воспроизводимая последовательность PL/clocks/reset |
| `qpsk-modem` | Композиция Linux/DTB/загрузки вокруг архивного FPGA-образа |
| `display-demo` | Образ, электрический интерфейс и проверка дисплея |

Офлайн-инвентаризация 2026-11-06 проверила 70 материализованных файлов из восьми
выбранных манифестов: размеры и SHA-256 совпали. Это архивное доказательство.
Исторический курсовой boot set требует `uImage`, которого в этом комплекте нет;
SD-кандидаты также объявляют отсутствующие пути к ядру. Встречаются и другие
отсутствующие пути. Эта проверка не делает кандидатов проверенными образами восстановления.
Нужно найти исходное ядро и его происхождение либо отдельно определить и
проверить новую загрузочную композицию. Нельзя подставлять случайное ядро или
пересчитывать исторические хеши ради успешного результата проверки.

Из корня приватного репозитория выполнить по порядку:

1. `python -m unittest discover -s tests -v`
2. `python verify_manifests.py --quiet --lfs-pointers`
3. `python verify_profiles.py --lfs-pointers --json-out firmware-profiles/inventory-local.json`

Приём LFS-поинтеров полезен в CI. Перед заявлением о побайтовой проверке повторите
проверку выбранных профилей без `--lfs-pointers` на материализованных файлах.
Приватный инструмент поддерживает `--payload-root` для отдельного клона с файлами.
Код возврата относится к целостности реестра/архива; загрузочные блокеры остаются
в отчёте даже при успешной проверке целостности. `uEnv.txt` разбирается как текст,
последнее повторное присваивание побеждает; команды не исполняются.
Объявленные пути считаются относительно каждого архивного SD-варианта;
это не доказательство активного пути загрузки.

## Отчёт по сохранённому наблюдению

Lab 6.3 читает сохранённый JSON без импорта libiio и обращения к плате.
Запускайте из корня публичного курса, результаты сохраняйте в приватном каталоге:

```bash
python blocks/block_06_rf_frontend_and_ad9363/python/lab_6_3_probe_iio_context.py --probe-json templates/iio_probe.synthetic.json --board-id synthetic-A --profile-id vendor-pluto --profile-report ../zynq-sdr-course-artifacts/evidence/issue81/synthetic-profile.json
```

В примере нет устройств и времени наблюдения: данные синтетические.
Для реального сохранённого probe замените путь и заявленные идентификаторы.
Отчёт содержит `source: saved-probe`, сохраняет время исходного наблюдения
(либо `null` для старых снимков), отдельно записывает время формирования отчёта.
Повторное чтение файла не подтверждает текущее развёртывание.

## Последующие этапы на стенде

Эти этапы требуют доступа к определённой плате и проверенной схемы восстановления/RF.
В рамках офлайн-инвентаризации они **не выполнялись**.

1. Зафиксировать плату, boot mode, serial boot log, Linux, идентичность FPGA
   и активные загрузочные файлы. Исходные IP/MAC/настройки хранить приватно.
2. Когда чтение обычных IIO-атрибутов допустимо для данной платы, получить
   наблюдение Lab 6.3 с явным URI. Например, заменив условное имя хоста:

   ```bash
   python blocks/block_06_rf_frontend_and_ad9363/python/lab_6_3_probe_iio_context.py --uri ip:BOARD_HOST --board-id A --profile-id vendor-pluto --json-out ../zynq-sdr-course-artifacts/evidence/issue81/A-probe.json --profile-report ../zynq-sdr-course-artifacts/evidence/issue81/A-profile.json
   ```

   Режим отчёта исключает чтение debug-атрибутов. Он читает обычные атрибуты,
   не создаёт буферы и не записывает настройки. Также читает TX LO `powerdown`,
   если он доступен; TX не заглушается и безопасность приёмника не устанавливается.
   Ошибки чтения и отсутствующие атрибуты фиксируются как наблюдения, а не успешные проверки.
3. Проверить откат **каждой** платы на отдельной SD-карте, сохранив исходный
   носитель. QSPI-архивы A/B различаются; дамп не является универсальной
   инструкцией восстановления. Команд записи QSPI в этом сценарии нет.
4. Отдельно проверить загрузку, PL reset, физический sample clock и RX DMA.
   Зафиксировать точные хеши файлов, serial-логи, число отсчётов, таймауты и ошибки.
   RX capture может менять настройки и создавать буферы: это отдельная операция.
5. Только затем измерять RF с записанными частотным планом, усилениями,
   аттенюацией, пределами приёмника и IQ-метаданными по [RF safety guide](../rf-safety.md).
   Использовать проверенный защищённый тракт; непроверенное прямое соединение TX–RX недопустимо.

## Протокол сравнения Software-QPSK и PL-QPSK

До измерений зафиксировать reference model, fixed-point форматы и ревизию HDL.
Использовать одинаковые payload/seed, отображение модуляции, преамбулу, символьную
частоту и частоту дискретизации, samples per symbol, RRC taps/roll-off и нормировку.
Различия квантования, clipping и транспорта записывать явно.

Для каждого запуска записать плату/профиль и хеши образов, LO/полосу, RX/TX gain,
RF-тракт/аттенюацию, формат/порядок/масштаб отсчётов, запрошенное и полученное
число отсчётов, ошибки DMA, clocks/reset и настройки синхронизации приёмника.
До замера задержки определить начальную/конечную точки и единицы; отдельно
учесть framing и транспорт. Сравнивать число пакетов, BER/PER и EVM в одинаковых
условиях. Потерянные и несинхронизированные пакеты включать в PER; знаменатель
BER и долю декодированных данных указывать отдельно: ошибки отсутствующих битов не наблюдались.
Результаты reference model, RTL, board loopback и измеренного RF вести в разных
колонках со ссылками на приватные исходные данные и очищенный публичный отчёт.
Протокол не содержит заявленных результатов производительности.
