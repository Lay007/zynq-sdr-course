# BPSK RTL блока 5: доказательства OOC-реализации в Vivado

[English version](block5-bpsk-vivado-evidence.md)

## Результат

Vivado 2021.1 синтезирует, размещает и разводит каждый BPSK-модуль RTL лабораторных 5.6-5.11 out
of context на кристалле курса `xc7z020clg400-2` с тактом `100 МГц`. Все 13 верхних модулей
полностью разведены, ошибок DRC нет. Входные и выходные порты проверяются так, будто каждый сосед —
регистр на том же такте (задержка входа и выхода 0 нс). **Двенадцать из тринадцати укладываются в
100 МГц; восстановление символьной синхронизации по Гарднеру — нет.**

## Что говорят числа

**RRC-фильтры дорогие.** Каждый 65-отводный фильтр полностью параллельный и симметричный:
проверенная стендом структура предварительно складывает зеркальные отсчёты и вычисляет 33
произведения за такт для I и для Q. Vivado отображает его на 96 DSP48E1, поэтому топ лабораторной
5.10 с фильтрами TX и RX занимает 192 из 220 DSP-блоков XC7Z020 (87 %). С таймингом всё спокойно
(дерево сумматоров регистрируется по стадиям); цена — площадь. Два наблюдения для будущей
оптимизации, здесь не измеренные: после 8-кратного повышения частоты семь из каждых восьми входных
отсчётов TX нулевые, поэтому полифазному фильтру TX нужна примерно восьмая часть умножителей, а
канал Q у BPSK на передаче не несёт информации.

Топ с AXI-Lite (лабораторная 5.11) использует на 48 DSP меньше, чем топ лабораторной 5.10, хотя
содержит тот же тракт данных. Топ 5.10 выводит `tx_q` на порт; топ с AXI-Lite открывает только
регистры, а Vivado удаляет логику, результат которой не доходит до выхода. Разница равна одному
каналу одного фильтра, что согласуется с удалением Q-тракта TX.

**Петля Гарднера не укладывается в 100 МГц.** `bpsk_symbol_timing_recovery` вычисляет всю петлю за
один такт: NCO -> умножение интерполятора (2 DSP48E1) -> знаковый детектор Гарднера -> ПИ-фильтр
петли -> следующий шаг NCO. Худший путь идёт от `nco_reg` к `w_step_reg` через 40 уровней логики
(28 из них — цепочки переноса) за 22,8 нс при бюджете 10 нс. Этот модуль — «подключаемая
альтернатива» лабораторной 5.8b и с параметрами по умолчанию не входит в топы 5.10/5.11, чей
сэмплер с фиксированной фазой `bpsk_symbol_timing_sampler` укладывается с запасом +5,065 нс. Выбор
между ними делает параметр `TIMING_RECOVERY` модуля `bpsk_rx_bit_recovery_chain` (по умолчанию 0,
фиксированная фаза). Чтобы петля работала на железе на 100 МГц, её нужно конвейеризовать. Фильтр
петли и шаг NCO обновляются только на стробе «on-time», раз в символ (каждые 8 входных отсчётов), а
интерполятор вычисляется на каждом стробе (примерно каждые 4 отсчёта), так что по собственной шкале
времени петли у обоих есть несколько тактов запаса; задача — разрезать путь, не меняя побитового
поведения петли.

**Оставшиеся критические пути — разветвление, а не логика.** В двух топах худший путь имеет 0-1
уровень логики и более 94 % трассировки: сигнал valid, управляющий разрешениями такта дерева
сумматоров согласованного фильтра (лабораторная 5.10), и сброс AXI, идущий на входы сброса
регистров произведений фильтра (лабораторная 5.11).

## Связь с прежними отчётами блока 5

[`block5-timing-summary.md`](block5-timing-summary.md) охватывает четыре вводных модуля
(`iq_passthrough`, `fir_iq_4tap`, `nco_mixer_iq`, `axis_iq_passthrough`) только синтезом и только
ограничением такта, поэтому пути от их портов не проверяются. Этот отчёт использует полный поток
OOC-реализации (размещение и трассировка) и проверяет порты.

## Воспроизведение

Из корня репозитория, при доступном Vivado через `VIVADO_BIN` или стандартный путь Xilinx:

```powershell
python tools/generate_block5_bpsk_vivado_reports.py
python tools/generate_block5_bpsk_vivado_reports.py --reuse    # разобрать заново без запуска Vivado
python tools/generate_block5_bpsk_vivado_reports.py --top bpsk_symbol_timing_recovery
```

Каждый верхний модуль собирается во временном проекте в памяти из закоммиченных исходников
`bpsk_*.v`: `synth_design -mode out_of_context`, `opt_design`, `place_design`, `phys_opt_design`,
`route_design`, затем отчёты по ресурсам, таймингу, статусу трассировки и DRC после синтеза и после
трассировки. Синтез запускается из корня репозитория, чтобы файлы `$readmemh` с коэффициентами и
битами кадра находились (в журнале `bpsk_rrc_tx_fir_taps.mem` отмечен как прочитанный успешно).
Проект, контрольные точки и bitstream не записываются. Ограничения для каждого модуля, исходные
отчёты и `block5_bpsk_vivado_ooc_metrics.json` лежат в `block5_bpsk_vivado_ooc_raw/`, строки с датой
и хостом нормализованы. Поток задаёт `general.maxThreads 1`; на машине с 16 ГБ запускайте один
процесс Vivado за раз.
