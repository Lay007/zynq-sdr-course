# OFDM RTL блока 8: доказательства OOC-реализации в Vivado

[English version](block8-ofdm-vivado-evidence.md)

## Результат

Vivado 2021.1 синтезирует, размещает и разводит каждый блок OFDM RTL блока 8 out of context на
кристалле курса `xc7z020clg400-2` с ограничением такта `100 МГц`. Все семь полностью разведены,
ошибок DRC нет. Два блока — построенные на общей бабочке radix-2 — **не укладываются в 100 МГц
с большим запасом**:

| Блок | LUT | FF | DSP48E1 | BRAM | WNS после трассировки на 100 МГц | Оценка |
|---|---:|---:|---:|---:|---:|---:|
| `ofdm_tx_cp16_path` (маппер, распределитель, IFFT64, вставка CP) | 8777 | 2276 | 4 | 0 | **-10,234 нс**, нарушают 1922 из 5155 конечных точек | около 49 МГц |
| `ofdm_cp16_remover` | 11 | 8 | 0 | 0 | +7,187 нс | |
| `ofdm_fft64_sequential` | 8938 | 2255 | 4 | 0 | **-10,769 нс** | около 48 МГц |
| `ofdm_subcarrier_extractor` | 16 | 0 | 0 | 0 | комбинационный, без такта | |
| `ofdm_one_tap_equalizer` | 148 | 72 | 4 | 0 | +7,141 нс | |
| `ofdm_pilot_phase_tracker` | 532 | 267 | 0 | 0 | +3,941 нс | |
| `ofdm_qpsk_demapper` | 3 | 0 | 0 | 0 | комбинационный, без такта | |

Оценка частоты — `1 / (период - WNS)`; она описывает разведённый критический путь, а не
охарактеризованный максимальный такт.

## Почему преобразования не укладываются в тайминг

Критический путь обоих преобразований одинаков, потому что `ofdm_fft64_sequential` переиспользует
ядро IFFT (`FFT(x)/N = conj(IFFT(conj(x)))`). Он начинается на счётчике стадий IFFT
(`ifft/stage_reg`), проходит через выбор операндов и поворотного множителя, комплексное умножение
(2 DSP48E1), сложение/вычитание, округление, насыщение Q1.15 и заканчивается на регистре
`saturation_count` бабочки — всё за один такт: 28 уровней логики (13 CARRY4) и задержка тракта
данных 20,2 нс (TX) / 20,8 нс (FFT) при бюджете 10 нс. Это прямое следствие задокументированного
контракта бабочки с задержкой в один такт.

Кроме того, преобразования держат 64-точечную рабочую память в регистрах и LUT, а не в блочной
памяти (0 тайлов BRAM, 80 LUT как распределённая RAM в TX-пути), поэтому они на два порядка больше
остальных блоков.

Что это исправило бы, по возрастанию стоимости: зарегистрировать произведения бабочки перед
сложением, вынести округление/насыщение и счётчик насыщений в следующую ступень (тот же шаблон, что
у FIR из Lab 5.2, где отдельная ступень округления/насыщения сдвинула WNS с -0,125 нс до +5,35 нс),
затем отобразить рабочую память в блочную RAM. Каждая дополнительная ступень бабочки меняет
расписание IFFT, поэтому вместе с ней должны меняться последовательный контроллер и его testbench.
Ничего из этого пока не сделано: RTL проверен симуляцией (побитово против Python-модели, BER 0 в
цифровых loopback), но пока не является проектом FPGA на 100 МГц.

## Воспроизведение

Из корня репозитория, при доступном Vivado через `VIVADO_BIN` или стандартный путь Xilinx:

```powershell
python tools/generate_block8_ofdm_vivado_reports.py
python tools/generate_block8_ofdm_vivado_reports.py --reuse    # разобрать заново без запуска Vivado
python tools/generate_block8_ofdm_vivado_reports.py --top ofdm_pilot_phase_tracker
```

Каждый верхний модуль собирается во временном проекте в памяти из закоммиченных исходников
`ofdm_*.v`: `synth_design -mode out_of_context`, `opt_design`, `place_design`, `phys_opt_design`,
`route_design`, затем отчёты по использованию ресурсов, таймингу, статусу трассировки и DRC после
синтеза и после трассировки. Проект, контрольные точки и bitstream не записываются. Исходные отчёты
и `block8_ofdm_vivado_ooc_metrics.json` лежат в `block8_ofdm_vivado_ooc_raw/`, строки с датой и
хостом нормализованы.

Замечание о прогоне: на машине, где снимался этот отчёт, многопоточный синтез дважды не смог
прочитать файл установки Vivado (`couldn't read file ... unimacro_vhdl.tcl`, затем `common.tcl`;
оба файла на месте). Поэтому поток теперь задаёт `general.maxThreads 1`. Остальные шесть модулей в этом отчёте
собраны до добавления этой настройки, с многопоточным синтезом.
