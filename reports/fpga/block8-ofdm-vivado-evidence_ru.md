# OFDM RTL блока 8: доказательства OOC-реализации в Vivado

[English version](block8-ofdm-vivado-evidence.md)

## Результат

Vivado 2021.1 синтезирует, размещает и разводит каждый блок OFDM RTL блока 8 out of context на
кристалле курса `xc7z020clg400-2` с ограничением такта `100 МГц`. Все семь полностью разведены,
ошибок DRC нет, и **все тактируемые блоки укладываются в 100 МГц** с конвейерным расписанием
IFFT/FFT, которое используется по умолчанию:

| Блок | LUT | FF | DSP48E1 | BRAM | WNS после трассировки на 100 МГц | Оценка |
|---|---:|---:|---:|---:|---:|---:|
| `ofdm_tx_cp16_path` (маппер, распределитель, IFFT64, вставка CP) | 8321 | 2421 | 4 | 0 | +1,694 нс | около 120 МГц |
| `ofdm_cp16_remover` | 11 | 8 | 0 | 0 | +7,187 нс | |
| `ofdm_fft64_sequential` | 7572 | 2391 | 4 | 0 | +1,227 нс | около 114 МГц |
| `ofdm_subcarrier_extractor` | 16 | 0 | 0 | 0 | комбинационный, без такта | |
| `ofdm_one_tap_equalizer` | 148 | 72 | 4 | 0 | +7,141 нс | |
| `ofdm_pilot_phase_tracker` | 532 | 267 | 0 | 0 | +3,941 нс | |
| `ofdm_qpsk_demapper` | 3 | 0 | 0 | 0 | комбинационный, без такта | |

Оценка частоты — `1 / (период - WNS)`; она описывает разведённый критический путь, а не
охарактеризованный максимальный такт.

## До и после: однотактная бабочка

Первая реализация использовала учебный базовый вариант, в котором общая бабочка radix-2 выполняет
весь тракт данных за один такт (`PIPELINED = 0`; этот режим по-прежнему доступен и проверяется в CI).
Тогда оба преобразования не укладывались в 100 МГц примерно на 10 нс:

| Блок | Базовый (`PIPELINED = 0`) | Конвейерный (по умолчанию) |
|---|---:|---:|
| `ofdm_tx_cp16_path` | WNS -10,234 нс, нарушают 1922 из 5155 конечных точек, 8777 LUT | WNS +1,694 нс, 0 нарушений, 8321 LUT |
| `ofdm_fft64_sequential` | WNS -10,769 нс, 8938 LUT | WNS +1,227 нс, 7572 LUT |
| Тактов вычисления IFFT на преобразование | 384 | 222 |

`ofdm_fft64_sequential` переиспользует ядро IFFT (`FFT(x)/N = conj(IFFT(conj(x)))`), поэтому
критический путь был общим: от счётчика стадий IFFT через выбор операндов и поворотного множителя,
комплексное умножение (2 DSP48E1), сложение/вычитание, округление, насыщение Q1.15 до регистра
`saturation_count` бабочки — всё за один такт: 28 уровней логики и 20,2 нс (TX) / 20,8 нс (FFT) при
бюджете 10 нс.

Исправление сохраняет арифметику побитно и меняет только расписание:

- `ofdm_ifft_butterfly` с `PIPELINED = 1` регистрирует входы, четыре произведения, округлённое
  произведение на поворотный множитель и поделённые пополам насыщенные выходы: задержка четыре такта,
  одна бабочка за такт.
- `ofdm_ifft64_sequential` выдаёт 32 бабочки стадии подряд, записывает каждый результат через четыре
  такта (адреса идут рядом по линии задержки) и между стадиями ждёт опустошения конвейера. Внутри
  стадии radix-2 каждая точка принадлежит ровно одной бабочке, поэтому чтения и записи не пересекаются.

Результат не только укладывается в тайминг, но и быстрее: 222 такта вычисления вместо 384. Все 16
OFDM-стендов проходят в обоих режимах (`python tools/run_ofdm_rtl.py` и `--baseline`), включая
побитовые векторы и оба цифровых loopback с BER = 0.

## Что ограничивает теперь

Новый критический путь уже не арифметический: это регистр состояния, управляющий разрешением записи в
64-точечную рабочую память (1 уровень логики, 8,1 нс, из них 92 % — трассировка). Преобразования
держат эту память в триггерах и LUT (0 тайлов BRAM, 80 LUT как распределённая RAM в TX-пути), поэтому
один управляющий сигнал разветвляется примерно на 2 тыс. триггеров. Перенос рабочей памяти в блочную
RAM — следующий шаг, если нужен больший запас или меньше LUT; при двух чтениях и двух записях за такт
в конвейерном расписании для этого нужна разбивка памяти на банки, а не один двухпортовый BRAM.

## Воспроизведение

Из корня репозитория, при доступном Vivado через `VIVADO_BIN` или стандартный путь Xilinx:

```powershell
python tools/generate_block8_ofdm_vivado_reports.py
python tools/generate_block8_ofdm_vivado_reports.py --reuse    # разобрать заново без запуска Vivado
python tools/generate_block8_ofdm_vivado_reports.py --top ofdm_pilot_phase_tracker
```

Каждый верхний модуль собирается во временном проекте в памяти из закоммиченных исходников
`ofdm_*.v`: `synth_design -mode out_of_context`, `opt_design`, `place_design`, `phys_opt_design`,
`route_design`, затем отчёты по использованию ресурсов, таймингу, статусу трассировки и DRC после
синтеза и после трассировки. Проект, контрольные точки и bitstream не записываются. Исходные отчёты и
`block8_ofdm_vivado_ooc_metrics.json` лежат в `block8_ofdm_vivado_ooc_raw/`, строки с датой и хостом
нормализованы. Числа базового варианта выше — из предыдущего прогона того же потока (коммит `8120687`).

Замечания о прогоне: поток задаёт `general.maxThreads 1`. На машине с 16 ГБ, где снимались отчёты,
параллельная работа Vivado упиралась в нехватку памяти, а выглядело это как вводящие в заблуждение
ошибки «couldn't read file» на собственных скриптах Vivado; запускайте один процесс Vivado за раз.
